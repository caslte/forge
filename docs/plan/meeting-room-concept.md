> 关联：`forge-v1-plan.md`、`meeting-room-demo.mjs`、`meeting-room-demo.html`、`meeting-room-demo-output.md`

## 1. 概述与定位

**需求**：多种模型从各自角度审核同一份方案/文档，互相质询，最终给出多模型都认可的结论（或如实呈现共识与分歧）。适用场景：PRD 评审、方案讨论、全部文档完成后多专家会审。

**定位**：**非 v1 MVP**。是 forge 未来 PRD 06（会议评审）的概念依据。v1 先做桌面工作台，会议室等 v1 多会话能力落地后再做（Phase 1 几乎顺手）。

## 2. 核心概念：编排器 + 对等 AgentSession（非子 agent）

**关键澄清**：会议室**不是子 agent**。

- **子 agent 模式**（pi 故意不支持）：一个 agent 内部 spawn 子 agent 干活，有父子关系。
- **会议室模式**（本方案）：一段**普通 TypeScript 代码（编排器，不会"思考"）**创建 N 个**对等的独立 AgentSession**（每个绑一个模型），安排发言顺序、传递发言稿、汇总。参与者之间无父子，都是平等独立 agent。

> pi 没有"子 agent"不影响本方案--会议室只是"用代码（而非用户）驱动多个独立 AgentSession"，正是 pi SDK 的正常用法。

## 3. 架构图

```
          ┌──────────────────────────────────────┐
          │        编排器（普通 TypeScript 代码）   │
          │   for 循环 / Promise.all / if 判断     │
          │   负责：发指令、收结果、把结果传给下一轮  │
          └────┬───────────────────────┬──────────┘
               │                       │
   ┌───────────▼──────────┐  ┌────────▼─────────────┐
   │  AgentSession A       │  │  AgentSession B       │
   │  model = 模型甲        │  │  model = 模型乙        │
   │  (独立·inMemory)       │  │  (独立·inMemory)       │
   └───────────┬──────────┘  └────────┬─────────────┘
               │ prompt()              │ prompt()
               ▼                       ▼
          模型甲 API                模型乙 API
```

- 每个 `prompt()` = 一次模型 API 调用（流式返回）。
- 编排器只是 `if/for/Promise.all`，自己不思考。
- 每会话独立 `ResourceLoader`（隔离事件总线+扩展）、独立 inMemory `SessionManager`。

## 4. 对话流程（demo 实现的 3 轮协议）

```
时间↓     ── 模型甲 (A) ──           ── 编排器 ──           ── 模型乙 (B) ──

          ┌───────────────┐                                ┌───────────────┐
 Round 1  │ A.prompt(文档) │                     ┌──────────│ B.prompt(文档) │
 并行评审  │ ← 评审A        │                     │          │ ← 评审B        │
 (互不知)  └───────┬───────┘                     │          └───────┬───────┘
                  │评审A                          │                  │评审B
                  └──────────────┐    ┌───────────┘                  │
                                 ▼    ▼                              
                          编排器收齐 [评审A, 评审B]
                                 │    │
                  ┌──────────────┘    └───────────┐                  │
                  │评审B给A看                     │ 评审A给B看        │
                  ▼                                ▼                  │
          ┌───────────────┐                                ┌─────────┴─────┐
 Round 2  │ A.prompt(评审B)│                     ┌──────────│ B.prompt(评审A)│
 交叉质询  │ ← 回应A        │                     │          │ ← 回应B        │
 (看对方)  └───────┬───────┘                     │          └───────┬───────┘
                  └──────────────┐    ┌───────────┘                  │
                                 ▼    ▼                              
                          编排器收齐 [回应A, 回应B]
                                 │ 把 评审A+回应A+评审B+回应B 全塞一个 prompt
                                 ▼
          ┌─────────────────────────────────────┐
 综合     │ A.prompt(评审A+回应A+评审B+回应B)     │  ← 复用 A 当综合者
          │ ← 综合结论(共识/分歧/建议)            │
          └─────────────────────────────────────┘
```

**调用次数**：N 个模型时，Round1=N，Round2=N，综合=1，共 **2N+1** 次 API 调用。demo（2 模型）= 5 次（模型甲 3 次：R1+R2+综合；模型乙 2 次：R1+R2）。

## 5. 两种模式

| 模式 | 输入 | 目的 |
|---|---|---|
| **评审模式** | 喂一份文档（PRD/设计/全部文档） | 找问题、给共识+分歧+建议 |
| **讨论模式** | 抛一个开放问题 | 多模型讨论收敛出方案 |

编排器一样，差别只是输入（文档 vs 问题）和 prompt 措辞。

## 6. 设计空间（要定的几件事）

| 维度 | 选项 | 倾向 |
|---|---|---|
| **协议** | ① 并行评审+综合 ② 多轮辩论 ③ 混合 | 先①后②（见分阶段）|
| **角色** | 指定专家角色 / 各自自然角度 / 两者 | 两者（默认自然角度，可选指定角色）|
| **终止** | 固定轮次+用户随时停 / 收敛检测 | **固定轮次+用户停**（收敛检测 LLM 不可靠，别做）|
| **产出** | 共识点 / 分歧点(各方立场) / 修改建议 / 修订版 | 全要 |
| **工具** | 纯推理评审 / 可用工具验证(读文件查一致性) | v1 纯推理；后续可加工具验证 |

## 7. 分阶段

- **Phase 1（最简，80% 价值）**：并行评审 + 综合 = N 个并行 AgentSession + 1 综合。多 AgentSession 已支持，编排代码很少。无真"对话"，但"多视角+汇总"已实现。
- **Phase 2（真"互相审核"）**：加交叉质询轮（每个看对方评审并回应）。demo 实现的就是这级（2 轮）。
- **Phase 3（深度）**：多轮辩论 + 投票批准轮（每个 approve/object+理由）-> 近似"都认可"。成本高，需用户控轮次/预算。

## 8. 诚实预期（重要）

"**多个模型都认为可以**"是理想，现实是"**多视角评审 + 综合**"。真"共识"靠 Phase 3 投票轮近似--LLM 不一定真收敛，可能永远有分歧。产出应**如实呈现共识与分歧**，而非假装一致。综合者给"推荐方案 + 未解决分歧"，人做最终决定。

## 9. 协同红利

- **多窗口画布 UI 复用**（PRD 02 SM-S05）：每个参与者一个窗口流式输出，最后综合面板。会议室=多窗口画布的"会议模式"。
- **多 AgentSession 能力复用**（PRD 02 TD-SM-01，已验证）。
- **模型配置复用**（PRD 05）：参与者模型从已配 provider 选。

## 10. demo 验证证据（2026-08）

用 `minimax-cn/MiniMax-M3` + `huoshan/ark-code-latest` 跑通了完整 3 轮（见 `meeting-room-demo-output.md` / `meeting-room-demo.html`）：

1. **架构 A 可行**：2 个对等 AgentSession 由 `Promise.all` 协调，跑通。
2. **多 AgentSession 并发运行时验证**：Round1/Round2 用 `Promise.all` **并发**跑 2 个 session，都独立成功产出，无冲突无崩溃--顺带验证了 PRD 02 TD-SM-01（源码分析说支持，运行时也证实）。
3. **真模型调用证据**：fetch 拦截确认 minimax 打到 `api.minimaxi.com`（200 + minimax `x-mm-request-id`）、huoshan 打到 `ark.cn-beijing.volces.com`；各自产出不同视角的实质评审。
4. **评审质量真实**：两个模型找出 forge 文档的真问题（HTTP-in-Electron 本地攻击面、桌面信任模型、utilityProcess、SQLite 存储等），且互相质询有同意/反对/补充，综合给出共识+分歧+Top3 建议。
5. **并发纪律印证**：每会话独立 `ResourceLoader`（隔离事件总线），无串扰。

> 计费备注：demo 的 minimax 调用打到官方中国站 + sk-cp key，minimax 后端处理（有 request-id）。coding plan 额度 0% 多为量小取整或账号差异（待用户拿 request-id 在 minimax 控制台核实），不影响"调用真实、架构可行"的结论。

## 11. 待定 / 下一步

- v1 不做。待 v1 多会话能力落地后，Phase 1（并行评审+综合）几乎顺手可做。
- 立项 PRD 06 时再定：协议选型、角色机制、轮次/预算上限、UI（会议模式 vs 复用多窗口画布）、是否加工具验证。
- demo 脚本 `meeting-room-demo.mjs` 可作为 Phase 1/2 的原型起点。
